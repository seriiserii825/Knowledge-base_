# Git tag

Тег — имя, которое указывает на конкретный коммит (`v0.9.0` → `0b144b1`).
Живёт в самом git-репозитории, переезжает через `git push` / `git clone`.
Release на GitHub — отдельно, см. `git-release.md`.

## Лёгкий и аннотированный

| | Лёгкий | Аннотированный |
|---|---|---|
| Создать | `git tag v0.1.0` | `git tag -a v0.1.0 -m "описание"` |
| Описание | нет — просто имя на коммите | есть + автор и дата тега |
| `git tag -n` | показывает сообщение коммита | показывает аннотацию |

Для версий — всегда аннотированный (`-a`).

## Создать новый тег

После коммита — ставится на текущий коммит (HEAD):

```
git add . && git commit -m "feat: ..."
git tag -a v0.1.3 -m "color-shade: short hex #RGB"
git push && git push origin v0.1.3     # или git push --tags
```

- На другой коммит: `git tag -a v0.1.3 <sha> -m "..."`.
- Без `-m` откроется редактор — для многострочного описания.
- `git push` теги **не пушит** — только явно (`origin v0.1.3` или `--tags`).
- Пушить аннотированные теги вместе с коммитами одной командой `git push`:
  `git config --global push.followTags true` (лёгкие всё равно отдельно).

py-sync-settings: `lft --push-tag v0.1.3 сообщение` — коммит, push, тег `-a`
с этим сообщением как аннотацией и push тега.

## Посмотреть

```
git tag                         # список
git tag -n                      # с аннотациями (лёгкие — сообщение коммита)
git tag --sort=-v:refname       # по версии, новые сверху
git tag --sort=-v:refname | head -1   # последний тег
git show v0.1.3                 # аннотация + коммит
git rev-parse v0.1.3^{commit}   # на каком коммите тег
```

На GitHub (вкладка Tags) аннотацию почти не видно — `…` рядом с тегом
показывает сообщение **коммита**. Аннотация видна на странице самого тега:
`github.com/<user>/<repo>/releases/tag/v0.1.3`.

## Добавить аннотацию к существующему тегу

Дописать нельзя — пересоздать с тем же именем **на том же коммите**:

```
git rev-parse v0.1.2^{commit}                  # запомнить коммит
git tag -a -f v0.1.2 v0.1.2 -m "описание"      # -f — перезаписать
git rev-parse v0.1.2^{commit}                  # должен быть тот же
git push --force origin v0.1.2
```

- Второй `v0.1.2` — «на тот коммит, где он сейчас».
- Для Go безопасно: checksum считается по содержимому коммита, не по объекту
  тега. Опасно только **переносить** тег на другой коммит — `checksum
  mismatch` (см. `Go/18.go-libs.md`).
- На другом ПК, где тег уже скачан, обновится только через
  `git fetch --tags --force`.

## Перейти на тег

```
git fetch --tags
git checkout v0.1.2        # detached HEAD — только смотреть/собрать
git checkout main          # вернуться
git clone --branch v0.1.2 <repo>   # клон сразу на теге
```

## Удалить

```
git tag -d v0.1.3                  # локально
git push origin --delete v0.1.3    # на GitHub
```

Для Go-модулей запушенный тег лучше не удалять и не переносить — делать
следующий (`v0.1.4`).

## Версии — какую цифру поднимать

- patch `v0.1.3` → `v0.1.4` — фикс, без изменения API;
- minor `v0.1.4` → `v0.2.0` — новая функция / команда / пакет;
- major `v1.0.0` → `v2.0.0` — ломающие изменения (Go: путь модуля
  `…/v2`).

Go (`go get …@v0.9.0`, `go install …@latest`) смотрит **только на теги**,
Release ему не нужен.
