# 03a. authorized_keys под root

Проблема: по умолчанию ключи лежат в `~/.ssh/authorized_keys`, и этот файл принадлежит самому пользователю. Если
злоумышленник выполнит код от имени `node` (взломанное приложение, плагин, зависимость), он допишет туда свой ключ и
сможет заходить по SSH.

Решение: хранить ключи в каталоге, который принадлежит **root**. Пользователь `node` (и всё, что запущено от него) их
читать может, менять — нет. Добавить ключ можно только через `sudo` (а для `sudo` нужен пароль `node`).

Перед этим: `03.vps-disable-root.md` — вход по ключу работает, пароли отключены.

> ⚠️ Держите открытой одну SSH-сессию до конца проверки. Если потеряли доступ — веб-консоль провайдера (OVH: KVM).

## Шаг 1. Создать каталог для ключей

```bash
sudo mkdir -p /etc/ssh/authorized_keys
sudo chown root:root /etc/ssh/authorized_keys
sudo chmod 755 /etc/ssh/authorized_keys
```

## Шаг 2. Перенести текущие ключи

Имя файла = имя пользователя.

```bash
sudo cp /home/node/.ssh/authorized_keys /etc/ssh/authorized_keys/node
sudo chown root:root /etc/ssh/authorized_keys/node
sudo chmod 644 /etc/ssh/authorized_keys/node

ls -la /etc/ssh/authorized_keys/   # владелец root, у node нет прав на запись
cat /etc/ssh/authorized_keys/node  # проверить, что ключи на месте
```

## Шаг 3. Указать sshd новое место

```bash
sudo vim /etc/ssh/sshd_config.d/00-hardening.conf
```

Добавить:

```sshconfig
AuthorizedKeysFile /etc/ssh/authorized_keys/%u
```

`%u` — имя пользователя, т.е. для `node` → `/etc/ssh/authorized_keys/node`. Файл в `~/.ssh/` больше не читается.

```bash
sudo sshd -t
sudo sshd -T | grep -i authorizedkeysfile   # → /etc/ssh/authorized_keys/%u
sudo systemctl restart ssh
```

## Шаг 4. Проверить (новый терминал)

```bash
ssh vps   # ✅ должен зайти
```

Если не пускает — в открытой сессии смотреть причину:

```bash
sudo journalctl -u ssh -n 30 --no-pager
```

Частая причина — права: каталог и файл должны принадлежать root и не быть доступны на запись группе/всем
(`StrictModes`).

## Шаг 5. Убрать старый файл

Только после успешного шага 4 — чтобы не было путаницы, какой файл реально используется:

```bash
mv ~/.ssh/authorized_keys ~/.ssh/authorized_keys.old
```

## Как теперь добавить новый ключ

`ssh-copy-id` больше **не работает** (он пишет в `~/.ssh/authorized_keys`). Добавлять вручную, на сервере:

```bash
echo "ssh-ed25519 AAAA... office-computer" | sudo tee -a /etc/ssh/authorized_keys/node
```

Удалить ключ (например, потерян ноутбук):

```bash
sudo vim /etc/ssh/authorized_keys/node   # удалить строку
```

Изменения применяются сразу, перезапуск sshd не нужен.

## Что это не защищает

Если злоумышленник получил **root** (или пользователя в группе `docker`, или `sudo` без пароля) — он может всё, включая
этот файл. Это защита от компрометации обычного пользователя, не от root.

Поэтому:

- `sudo` — только с паролем (не добавлять `NOPASSWD` в sudoers);
- приложения (WordPress, Node) запускать не от `node`, а в контейнерах / от отдельных пользователей без sudo.
